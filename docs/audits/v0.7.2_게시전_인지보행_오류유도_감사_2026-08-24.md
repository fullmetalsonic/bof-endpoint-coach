감사일: 2026-08-24  
대상: v0.7.2 로컬 릴리스 후보  
선행 감사: `v0.7.2_투입코치_기능_UI_UX_데이터_회귀감사_2026-08-24.md`

## 1. 왜 다시 검사했는가

선행 감사는 정상 입력을 중심으로 기능·계산·백업·브라우저 회귀를 폭넓게 확인했다. 이번에는 같은 시험을 반복하지 않고 다음 질문으로 다시 보았다.

1. 처음 보는 작업자가 다음 행동을 버튼 이름만 보고 맞힐 수 있는가?
2. 화면에서 누를 수 있는 버튼은 어떤 허용 입력에서도 성공하거나, 실패 이유를 화면에 표시하는가?
3. 저장·채택·닫기처럼 결과가 다른 행동이 비슷한 표현으로 보이지 않는가?
4. 입력 도중 다른 행동을 했거나 창을 닫아도 오래된 초안이 의도치 않게 남지 않는가?
5. 1920×1080 업무 화면을 짧게 훑을 때 경계·단위·현재 행동이 우선 보이는가?

검사 방법은 `초보자 인지보행`, `오류 유도`, `상태 전환표 대조`, `중단·재진입`, `시각적 정보 우선순위`다.

- 기존 v0.7.2 화면 6장을 다시 육안 확인했다. 대시보드는 기존 전문형 Data Ledger 구조를 유지하고, 문헌 참고안과 실제 투입 기록의 경계를 반복 표시한다.

## 3. 새로 발견한 문제

### HIGH-01 — 조건부 시점값이 비어 있어도 `내 계획 저장`이 활성화됨

재현 조건:

1. DEMO G6에서 `비교 보기` 또는 `내 계획`을 연다.
2. 예상량은 기본값을 둔다.
3. 예정 기준을 `취련 경과` 또는 `누적 산소`로 바꾼다.
4. 새로 나타난 경과분 또는 누적 산소 입력은 비운다.
5. `내 계획 저장`이 활성 상태로 남는다.

확인 근거:

- 화면 활성 조건은 예상량과 재료만 검사한다.
- 도메인 검증은 빈 경과분을 `plan_elapsed_invalid`, 빈 누적 산소를 `plan_oxygen_invalid`, 장입 전 로컬 시각을 `plan_time_invalid`로 거부한다.
- 즉, 화면의 “누를 수 있음”과 저장 규칙이 서로 다르다. 정상적인 화면 조작만으로 저장 실패 경로에 들어가며 현재 비교창에는 해당 오류를 설명하는 인라인 메시지가 없다.

판정: 공개 릴리스 차단. 조건별 유효성, 필드 오류 문구, 실패 포착, 회귀시험이 필요하다.

### MEDIUM-01 — `내 계획 유지`가 계획 저장처럼 읽히지만 결정 이력만 추가함

- 비교창 안에는 `내 계획 저장`과 `내 계획 유지`가 함께 있다.
- `내 계획 유지`는 입력 중인 값을 저장하지 않고 `keep_operator_plan` 결정 이력만 추가한다.
- 실행 후 창을 닫지 않고 완료 안내도 없어 눌렸는지 알기 어렵다.
- 같은 버튼을 반복 누르면 같은 제안에 결정 이력이 중복될 수 있다.

판정: 바쁜 작업자가 미저장 입력을 저장했다고 오해할 가능성이 있다. `저장된 내 계획 채택`처럼 의미를 바꾸고, 저장된 활성 계획이 있을 때만 허용하며, 완료 후 닫기·알림·중복 방지가 필요하다.

### MEDIUM-02 — `코치안을 계획으로 복사` 후 기존 미저장 초안이 남을 수 있음

- 수동 예상량을 입력해 자동보관 초안이 생긴 뒤 `코치안을 계획으로 복사`하면 코치값은 새 계획으로 저장된다.
- 그러나 현재 입력 폼과 자동보관 초안은 복사한 값으로 정리되지 않는다.
- 창을 다시 열었을 때 오래된 수동 초안이 복원되어, 방금 복사한 계획이 사라졌거나 복사가 실패한 것처럼 느낄 수 있다.

판정: 복사 성공 후 폼을 저장된 값과 동기화하고 초안을 확정하거나, 창을 닫고 명시적 완료 알림을 보여줘야 한다.

### MEDIUM-03 — 판단 보조문과 일부 단위가 8~10px로 너무 작음

- 문헌 시험 배지, 신뢰 상태, 단위 설명, 표의 제외 사유, 오차학습 상태 등 판단에 필요한 보조정보 상당수가 CSS상 8~10px다.
- 주 행동과 핵심 숫자는 더 크고 구조도 명확하다는 장점이 있으나, 1920×1080 모니터를 멀리서 보거나 Windows 배율이 다른 경우 보조 경계를 놓칠 수 있다.
- 이는 반응형 가로 넘침 시험으로는 발견되지 않는 인간공학 위험이다.

판정: 현장 조업 화면의 의사결정 관련 최소 글자 크기와 대비 기준을 별도로 정하고, 실제 회사 PC 배율에서 확인해야 한다. WCAG 전체 준수는 이번 감사로 주장하지 않는다.

### MEDIUM-04 — 긴 투입모델 설정 화면에서 저장 제어가 페이지 상단에만 있음

- 핵심 계수·문헌값·조작별 한도·허용 단계·재료별 고급값을 아래쪽에서 수정한다.
- 변경 사유와 `설정 저장`은 상단에 있어 긴 화면을 다시 올려야 한다.
- 저장 전 검토가 필요한 설정이라는 점은 타당하지만, 수정 직후 저장 위치를 잃기 쉽다.

판정: 상단 저장 제어를 고정하거나 하단에 같은 상태를 공유하는 저장 막대를 제공하는 개선이 권장된다.

## 4. 잘 된 점

- 대시보드에서 현재 G단계의 주 행동과 단계 전환이 분리되어 있다.
- `문헌 시험`, `계획만 저장·실제값 아님`, `실제 투입은 별도 기록`, `초안만 생성` 경계가 숫자 가까이에 있다.
- 투입 코치는 선택 사항이며 접거나 보지 않아도 G단계를 막지 않는다.
- 실제 투입 기록은 하단의 큰 업무 버튼으로 분리되어 계획값이 실제값으로 섞이지 않는다.
- 자동저장, JSON 백업, 복구카드, 설정 버전은 서로 다른 복구 수단으로 구성되어 있다.

## 7. 추가 실패 주입에서 발견해 함께 수정한 문제

### MEDIUM-05 — 계획 저장 성공과 비교 판단 실패를 한 결과로 취급

코치안을 계획으로 복사할 때 계획 저장은 성공했지만 비교 판단 이력만 실패하면 과거 구현은 전체를 저장 실패처럼 오해하게 하거나 성공처럼 표시할 수 있었다. 두 저장 결과를 분리해 확인하고, 부분 성공이면 `계획은 저장됨 / 판단 이력은 실패`를 정확히 알리도록 수정했다.

### MEDIUM-06 — 보류 결정 저장 실패인데 비교창이 닫힘

`샘플 후 다시 보기`가 결정 저장 결과를 확인하지 않고 즉시 창을 닫았다. 이제 성공할 때만 닫고, 실패·예외이면 창을 유지한 채 오류를 표시한다.

### MEDIUM-07 — 비교 열람이 새 제안을 만들 때 미저장 계획 초안이 복원되지 않음

초안 호환 버전에 매번 바뀌는 제안 ID를 사용해, 창을 닫고 다시 열 때 새 제안이 생성되면 직전 수동 초안이 호환되지 않는 것으로 처리됐다. 초안 버전을 `차지 ID + G단계 + 계획 스키마`로 고정해 같은 단계의 수동 초안은 새 계산 제안이 생겨도 복원하고, 단계가 바뀌면 이전 단계 초안을 섞지 않도록 수정했다.

### MEDIUM-08 — 같은 제안의 코치안 복사를 반복하면 동일 계획 버전이 늘어남

결정 원장은 멱등 처리됐지만 계획 저장은 별도이므로, 같은 비교창에서 복사 버튼을 다시 누르면 동일한 계획 버전이 하나 더 생길 수 있었다. 복사·결정이 모두 성공하면 버튼을 `코치안 복사 기록됨`으로 바꾸고 비활성화해 같은 제안의 중복 복사를 막았다. 저장 잠금 상태로 비교만 가능한 경우에는 창 안에도 잠금 이유와 해결 위치를 표시했다.

## 9. 원격 게시 전 문서 정합성 재감사

- GitHub README를 실제 브라우저에서 확인하다 로컬 개발 설명의 시험 수가 교정 전 `165개`로 남은 것을 발견해 `174개`로 수정했다.
- 계획 비교 스크린샷은 v0.7.2 초기 후보의 `내 계획 유지` 버튼을 포함한다. 이미지를 최종 화면처럼 오인하지 않도록 README와 상세 설명서에 캡처 경계를 명시하고, 최종 버튼명·활성 조건·피드백은 본문과 E2E로 확인한다.
- 외부 HTML 미리보기 서비스는 단일 HTML 스크립트를 정상 실행하지 못했고, 다른 공개 프록시는 별도 외부 콘텐츠 확인을 요구했다. 경고를 임의로 승인하지 않았으며, 해당 서비스의 실패를 제품 실패로 계산하지 않았다.

## 10. 공개 저장소 보안·오프라인 경계 감사

- 추적 소스와 v0.7.2 배포 HTML에서 회사 이메일, GitHub 토큰 형식, 개인키 머리말, Bearer 자격증명, 비밀번호 입력 요소를 집중 검색해 0건임을 확인했다.
- `app/src`에서 `fetch`, `XMLHttpRequest`, `WebSocket`, `sendBeacon` 호출이 없고, v0.7.2 단일 HTML에 외부 HTTP(S) `src`·`href` 의존성이 없음을 확인했다.
- `npm audit --audit-level=moderate`는 취약점 0건이었다.
- 이 검사는 공개 산출물에 알려진 비밀·외부 통신 경로가 없다는 정적 확인이다. 회사 PC의 보안 정책 허용 여부와 실제 운영 데이터의 반출 방지는 별도 현장 절차로 검증한다.
