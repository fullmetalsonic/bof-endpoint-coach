# 취련 코치 v0 구현 준비도 비판 감사

감사일: 2026-08-22  
감사 범위: 제품·도메인·UI·디자인·데이터·기존 감사 문서의 요구사항 정합성  
감사 방식: 문서 기반 요구사항 감사. HTML 구현물과 실제 현장 데이터가 없으므로 클릭 흐름, 브라우저 동작, 계산 정확도, 실제 사용성은 검증하지 못했다.

## 결론

**구현 착수: 보류 권고.**

방향과 화면 구조는 충분히 구체적이지만, 입력 화면을 만들기 전에 결정해야 할 데이터·계산·복구 계약이 아직 있다. 이 상태로 구현하면 화면은 만들 수 있어도, 참고 예상값의 근거 재현과 공용 PC의 이력 복구를 보장할 수 없다.

| P0 | 최초 7건 중 4건 미해결 | 미해결 항목 전에는 계산·승인 관련 구현을 시작하지 않음 |
| P1 | 5 | 첫 현장 시범 전까지 정의 필요 |
| 확인 필요 | 4 | 현장 담당자와 확인해야 하며 개발자가 임의 결정하면 안 됨 |

## 이미 잘 잡힌 기반

- 자동 제어·실시간 연동·AI 지시를 v0에서 제외했다.
- 기준값 버전, 원본 단위와 환산값, 수동 입력 시점 분리를 정의했다.
- CSV를 복원 원본, XLSX를 읽기용 보고서로 구분했다.
- G0~G8과 재샘플·재취련·출강의 흐름을 기록 대상으로 잡았다.
- 실제 조성·목표·수율을 공개 자료 기본값으로 넣지 않도록 막았다.

## P0 — 구현 전 반드시 닫아야 할 공백

### P0-01. 품질 항목 표시 규칙이 문서 안에서 충돌한다

**증거**

- `domain/품질관리항목_초안.md`는 기본 품질 후보를 C·온도·P·S·Mn·Si 6개로 정의한다.
- `ui/UI_기능구성_초안.md`의 기존 동적 행 구성에는 C·온도·P·Mn 예시와 `기본 최대 4~5개`가 남아 있다.

**위험**: 구현자가 어느 규칙을 따르느냐에 따라 화면 밀도와 설정 화면의 동작이 달라진다.

**필요 결정**: `품질관리항목_초안.md`를 유일한 항목 수·분류 기준으로 지정하고, UI 문서의 기존 4~5개 규칙을 제거 또는 명시적으로 대체한다.

**처리 상태 (2026-08-22)**: 해결. `ui/UI_기능구성_초안.md`의 기본 4~5개 규칙을 기본 후보 6개(C·온도·P·S·Mn·Si)와 강종 특화 성분 상세 규칙으로 대체했다.

### P0-02. 참고 계산의 입력·출력·불확실성 계약이 없다

**증거**: 계산 허용 조건과 `참고 예상` 표시는 정의됐지만, 어떤 입력 조합으로 어떤 결과(투입량, 종점 성분, 온도, 범위)를 계산하는지와 결과 단위·반올림·오차 표현이 정의되지 않았다.

**위험**: 동일 차지에 대해 구현마다 다른 수치가 나오거나, 입력 부족 상태에서 그럴듯한 예상값을 표시할 수 있다.

**필요 산출물**: `계산명세` 문서별로 목적, 사용 입력, 제외 조건, 단위/반올림, 기준 버전, 결과의 참고 문구, 테스트 예시(가상 수치)를 정의한다. 공정 식과 수치는 현장 승인 전까지 비워 둔다.

**처리 상태 (2026-08-22)**: 부분 해결. 수동 입력한 취련 시작·조업 패턴/풍량·투입·샘플·분석과 PC 로컬 시간에 따른 재계산 입력 규칙은 `domain/시간경과형_참고예상_입력규칙_초안.md`에 정의했다. 계산 논리와 현장 종점 예측 정확도를 분리하고, 가상 계산 검증 → 시간순 독립 검증 → 그림자 예상 → 현장 승인 절차를 `product/종점참고예상_검증및승인계획_초안.md`에 정의했다. 실제 계산식·출력·반올림·가상 시험값·현장 오차 기준은 여전히 미해결이다.

### P0-03. 이벤트·정정·게이트 상태 모델이 충분히 기계적으로 정의되지 않았다

**증거**: 이벤트 유형과 G0~G8은 있으나, 게이트 이동/되돌림, 차지 취소·재개, 중복 이벤트, 정정 이벤트가 현재값을 어떻게 바꾸는지가 하나의 규칙으로 정의되지 않았다.

**위험**: 재취련 후 새 분석값, 잘못 입력한 투입량, 순서가 뒤늦게 들어온 이벤트에서 현재 화면과 CSV 복원이 달라질 수 있다.

**필요 산출물**: 이벤트 ID, 차지 ID, 발생/기록 시각, 생성/정정/무효 상태, 대상 이벤트 ID, 게이트 전환 조건, 현재값 선택 우선순위를 가진 이벤트 상태표를 만든다.

### P0-04. 샘플과 분석 결과의 생명주기가 부족하다

**증거**: 샘플 ID·채취 시각·분석 입력은 있지만, 재분석/재시험, 동일 샘플의 수정 결과, 분석 방법·출처, 최종 채택 결과 선택 규칙이 없다.

**위험**: 어떤 분석값이 범위 막대·참고 계산·출강 검토에 쓰였는지 재현할 수 없다.

**필요 결정**: 샘플은 여러 분석 결과를 가질 수 있는지, 결과 정정은 새 레코드인지, 최신값은 채취 시각/입력 시각/명시적 채택 중 무엇을 따르는지, 분석 방법·입력 출처를 기록할지 정한다.

### P0-05. 공용 PC 저장·복원 전략이 운영 문장 수준에 머문다

**증거**: IndexedDB는 편의 기능이고 CSV를 정기 백업한다는 원칙은 있으나, 저장 실패·브라우저 초기화·PC 교체·부분 손상·중복 복원 시의 복구 절차와 사용자 확인 화면이 없다.

**위험**: 데이터가 사라졌거나 일부만 저장됐는데 작업자가 정상으로 오해할 수 있다.

**필요 결정**: 저장 완료 기준, 자동 저장 표시, 마지막 정상 백업, 백업 전 읽기 검사, 복원 전 데이터 건수 비교, 실패 시 원본 보존과 복구 안내를 정의한다.

**처리 상태 (2026-08-22)**: 해결. 저장/백업 생성/다운로드 요청/선택 파일 검증을 분리하고, 전체 CSV 묶음·빈 저장소 복원·복원 전후 검사·실패 시 무변경 규칙을 `domain/CSV_백업복원_계약_v0_초안.md`에 정의했다.

### P0-06. CSV 계약이 스키마 수준까지 내려가지 않았다

**증거**: UTF-8·스키마 버전·원자적 복원·충돌 시 건너뜀/취소는 정해졌지만, 파일 구성(한 파일/여러 CSV), 식별자 규칙, 필수 열·자료형·소수점·줄바꿈, 참조 무결성, 버전 이관, CSV 수식 주입 방어가 없다.

**위험**: Excel에서 편집된 백업, 지역별 쉼표/소수점, 오래된 스키마 파일에서 조용한 데이터 변형·누락이 생길 수 있다.

**필요 산출물**: CSV 스키마 사전, 예시 파일, 유효/무효/중복/구버전 복원 시나리오, 내보내기 문자 이스케이프 규칙을 만든다.

**처리 상태 (2026-08-22)**: 해결. 필수 CSV 파일·고정 열 역할·manifest·UTF-8·행 수·SHA-256·참조 검사·Excel 텍스트 이스케이프·복원 제한을 `domain/CSV_백업복원_계약_v0_초안.md`에 정의했다. 실제 CSV 예시와 구현 테스트는 남아 있다.

### P0-07. 역할명 기록은 인증이나 권한 통제가 아니다

**증거**: 설정 승인·중지·CSV 가져오기에는 역할명·시각·사유를 남기지만, 공용 PC에서 누구든 입력할 수 있다.

**위험**: 승인된 기준처럼 보이는 값의 신뢰 수준이 실제보다 높아질 수 있다.

**필요 결정**: v0을 `승인 기준을 조회·기록하는 보조도구`로 한정할지, 아니면 현장 책임자가 설정 파일을 별도 승인·반입하는 절차를 둘지 정한다. 계정 없는 HTML에 보안 권한이 있다고 주장하지 않는다.

## 현장 확인 없이는 정할 수 없는 항목

1. 강종군별 실제 활성 품질 항목과 기본 6개 적용 범위
2. 최신 분석의 유효 시간, 재샘플·재취련·출강 검토의 실제 승인 흐름
3. 기준값을 초안에서 승인으로 바꾸는 사람과, 계정 없는 v0에서의 반입 절차
4. 분석 결과를 입력하는 실제 역할·전달 방식과 인계 메모의 현장 사용 방식

### P1-02 처리 상태 (2026-08-22)

- 동시 진행 차지는 `진행 중 차지 목록`에서 클릭 전환하고, 선택된 한 차지만 입력 대상으로 고정하는 방식으로 결정했다.
- 미저장 입력 전환 확인, 차지 ID 고정 표시, 차지별 백업 범위, 오입력 방지 규칙을 `ui/동시진행_차지_전환규칙_초안.md`에 기록했다.
- 실제 동시 차지 수, 인계 메모의 필요성, 분석 입력 역할은 현장 검토가 남아 있다.

## 권고 구현 순서 재조정

```text
P0-01 품질 규칙 단일화
→ P0-02 계산 명세
→ P0-03 이벤트/게이트 모델
→ P0-04 샘플·분석 모델
→ P0-05 저장·복구
→ P0-06 CSV 계약
→ P0-07 운영상 승인 경계
→ 가상 데이터 기반 시나리오 테스트
→ 화면 구현
```

이 순서를 지키면 화면을 먼저 만들고 나중에 데이터 구조를 다시 뜯어고치는 위험을 낮출 수 있다.

## 검증 한계

- 실제 취련사, 품질 담당자, 현장 책임자의 검토는 아직 받지 못했다.
- 실제 조업 수치·분석표·보안 정책·브라우저 정책이 없으므로 공정 정확도·보안 적합성·입력 시간은 미검증이다.
- HTML이 없으므로 저장 실패, CSV/XLSX 호환성, 키보드 사용성, 화면 해상도, 접근성은 테스트하지 못했다.
