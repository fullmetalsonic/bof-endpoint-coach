# 디버그·재발방지 대장

상태: 운영 중  
목적: 같은 원인으로 다시 코드를 의심하거나 수정하는 일을 막기 위해 **증상, 재현, 원인, 증거, 영구 차단책**을 따로 관리한다.

## 디버그 전 고정 순서

브라우저 시험 결과가 예상과 다르면 코드를 수정하기 전에 아래 순서로 확인한다.

1. 시험 명령이 현재 `app` 작업공간에서 실행됐는지 확인한다.
2. 5173 포트를 다른 개발 서버가 점유하는지 확인한다.
3. 실행 앱 버전과 그 버전의 필수 소스 표식을 확인한다.
4. 기존 서버를 재사용하지 않고 현재 작업공간에서 새 서버를 시작한다.
5. 같은 증상을 새 서버에서 재현한 경우에만 코드 결함 분석으로 넘어간다.

표준 명령은 `app` 폴더의 `npm run test:e2e`다. 이 명령은 사전검사에서 현재 작업공간·버전·필수 소스 표식·5173 포트 상태를 검사하며, 하나라도 맞지 않으면 시험을 시작하지 않는다.

## DBG-2026-08-24-001 — 구형 개발 서버가 최신 소스 대신 이전 작업공간을 제공

### 증상

- 최신 소스에 있는 투입모델 설정이 브라우저에서는 없는 것처럼 보였다.
- 설정 저장 버튼과 JSON 요약 시험이 새 구현과 맞지 않게 실패했다.
- 같은 종류의 실패를 소스 문제로 오인해 코드 확인과 수정 루프를 반복했다.

### 재현과 원인

1. 이전 작업 때 시작한 Vite 서버가 5173 포트에서 계속 실행 중이었다.
2. Playwright 설정의 `reuseExistingServer: !process.env.CI`가 로컬 시험에서 그 서버를 정상 서버로 간주했다.
3. 현재 Playwright 시험은 새 코드였지만 브라우저가 받은 화면·모듈은 구형 서버의 소스였다.

### 확인 증거

- 5173 포트를 점유한 Node 프로세스의 시작 시각이 현재 개발 세션보다 이전이었다.
- 해당 서버가 제공한 `referenceSettings.js`에는 최신 필드 `additionModelProfiles`가 없었다.
- 구형 서버를 종료하고 현재 작업공간에서 새 서버로 실행하자 격리 시험과 Chromium 전체 29건이 통과했다.

### 잘못된 접근

- 브라우저가 실제로 어떤 작업공간을 제공받았는지 먼저 확인하지 않았다.
- 기존 서버 재사용을 편의 기능으로 남겨 두어 시험 소스와 제공 소스가 달라질 수 있게 했다.
- 디버그 사건을 독립 대장과 자동 차단 규칙으로 남기지 않아 같은 확인을 반복했다.

### 수정과 영구 차단책

- `playwright.config.mjs`의 기존 서버 재사용을 항상 금지했다.
- `npm run test:e2e*` 앞에 자동 사전검사를 연결했다.
- 사전검사는 현재 작업공간, 앱 이름·버전, 버전별 필수 소스 표식, 5173 포트 비점유를 확인한다.
- 5173 포트가 이미 열려 있으면 자동 종료하지 않고 시험을 차단해 잘못된 프로세스 종료와 구형 서버 재사용을 모두 피한다.
- 앱 버전이 바뀔 때는 사전검사의 버전별 소스 계약도 반드시 추가해야 한다. 누락하면 시험을 차단한다.
- 프로젝트 `AGENTS.md`와 개발검증 체크리스트에 같은 규칙을 고정했다.

### 재검증

- 정상 상태에서 `npm run test:e2e:preflight`가 현재 경로·v0.7.2·필수 표식·빈 포트를 확인하고 PASS했다.
- 임시 HTTP 서버로 5173 포트를 의도적으로 점유하자 `E2E_PORT_ALREADY_IN_USE`로 종료코드 1을 반환하고 시험을 시작하지 않았다.
- 임시 서버를 종료한 뒤 같은 표준 명령으로 사전검사를 통과하고 새 Vite 서버를 시작해 Chromium 전체 29건이 PASS했다.
- 사전검사 단위시험 4건과 관련 ESLint가 PASS했다.

## DBG-2026-08-24-002 — Chrome 채널의 datetime-local `:00` 시험값 거부

### 증상과 원인

- 설치형 Chrome 전체 회귀시험 29건 중 출강 시각 정정 1건이 `locator.fill: Malformed value`로 실패했다.
- 시험은 원래 출강시각에서 1초를 뺀 `YYYY-MM-DDTHH:mm:ss` 값을 만들었다. 실행 시각의 초가 `01`이면 결과가 정확히 `:00`이 됐다.
- Chromium 번들에서는 통과했지만 설치형 Chrome은 초 단위 형식이 `:00`인 datetime-local 입력을 Playwright `fill`에서 거부했다. 제품의 시각 검증이나 저장 실패가 아니라 시험값 직렬화 경계였다.

### 영구 차단책

- 분 단위로 잘라 초를 없애면 실제 시각 역행 검증이 거짓 실패할 수 있으므로 기존 `slice(0, 19)` 초 보존 원칙은 유지한다.
- 정정 시험값이 정확히 `:00`이면 1초를 더 빼 `:59`로 만들고, 실제 발생시각보다 이전이라는 시험 목적을 그대로 유지한다.
- 설치형 Chrome 격리 재시험과 전체 재시험, Edge 전체 시험으로 회귀 여부를 확인한다.

### 재검증

- 설치형 Chrome 격리 시험 1/1 PASS.
- 설치형 Chrome 전체 29/29 PASS.
- 설치형 Edge 전체 29/29 PASS.
- 같은 수정이 포함된 Chromium 전체 29/29 PASS.

## DBG-2026-08-24-003 — 투입 계획 화면과 저장 규칙·초안 수명주기 불일치

### 증상

- `취련 경과`·`누적 산소` 기준값이 비어 있어도 저장 버튼이 활성화되지만 실제 저장은 거부됐다.
- 비교 결정 저장이 실패해도 `샘플 후 다시 보기` 창이 닫히거나, 계획 저장과 판단 저장의 부분 성공을 정확히 구분하지 못했다.
- 미저장 수동 계획을 입력하고 비교창을 다시 열면 열람 시 생성되는 새 제안 ID 때문에 초안이 복원되지 않을 수 있었다.

### 재현과 원인

1. 화면은 예상량·재료만 따로 검사했고 도메인은 예정 기준별 필수값까지 검사해 두 규칙이 갈라졌다.
2. 일부 판단 버튼은 `onDecision`의 성공·실패를 확인하지 않고 창을 닫거나 성공 흐름을 계속했다.
3. 초안 호환 버전에 매번 바뀌는 제안 ID를 사용해, 같은 차지·같은 G단계의 수동 초안도 새 제안이 생기면 구형으로 판정됐다.

### 수정과 영구 차단책

- UI와 저장 훅이 `validateOperatorPlanInput` 하나를 함께 사용한다.
- 저장·복사·채택·보류의 성공, 실패, 부분 성공을 각각 확인하고 화면에 표시한다.
- 동일 제안·동일 판단은 도메인에서 멱등 처리해 결정 원장과 조업 로그를 중복 생성하지 않는다.
- 복사 성공 시 폼·확정 스냅샷·로컬 초안을 같은 값으로 동기화한다.
- 같은 제안의 복사·결정 성공 뒤에는 복사 버튼을 완료 상태로 바꿔 동일 계획 버전의 반복 생성을 막는다.
- 계획 초안 호환 버전은 `차지 ID + G단계 + 계획 스키마`로 관리해 제안 갱신과 분리한다.
- 회귀시험에 조건부 입력 3종, 반복 클릭, 저장 실패, 부분 성공, 보류 실패, 제안 갱신 뒤 초안 복구를 고정한다.

### 재검증

- 관련 Vitest 3파일·15시험 PASS.
- 전체 `npm run check`: ESLint, Vitest 35파일·174시험, 일반·Sites·단일 HTML 빌드, Sites 4시험 PASS.
- 이번 교정본의 실브라우저 시각·E2E는 인앱 브라우저의 로컬 `file://` 정책 때문에 실행하지 못했으며 PASS로 기록하지 않는다.

## DBG-2026-08-24-004 — 앱 버전만 올리고 같은 버전의 전달 문서를 모두 생성하지 않음

### 증상

- v0.7.3 첫 Chromium 전체 E2E 31건 중 발표용 설명서, 구두 기능 소개서, 메일 미리보기 3건이 `ERR_FILE_NOT_FOUND`로 실패했다.
- 앱·사용 설명서·상세 설명서·README HTML은 있었지만, E2E가 현재 패키지 버전으로 찾는 나머지 세 파일은 v0.7.2까지만 존재했다.

### 원인

- 기능·코드 버전과 일부 문서만 v0.7.3으로 올리고, 버전별 원본이 필요한 발표·구두 소개 문서를 만들지 않았다.
- 전체 E2E를 실행하기 전에 새 버전의 전달 HTML 6종 존재를 한 묶음으로 확인하지 않았다.

### 수정

- v0.7.3 발표용·구두 기능 소개 원본에 선택형 용존산소 설명과 실제 화면을 추가했다.
- 사용자·상세·발표·구두 소개·README·메일 미리보기 HTML을 모두 v0.7.3 파일명으로 다시 생성했다.
- 첫 실패 결과를 PASS로 바꾸지 않고, 수정 뒤 Chromium·Chrome·Edge 전체 31건을 각각 처음부터 재실행했다.

### 영구 차단책

- 개발검증 체크리스트의 문서 항목에 앱 버전 변경 직후 전달 HTML 6종의 같은 버전 파일 존재 확인을 추가했다.
- 동적 문서 E2E는 현재 `package.json` 버전의 파일을 계속 요구한다. 예전 버전 파일로 대체하거나 시험을 건너뛰지 않는다.

### 재검증

- Chromium 31/31 PASS.
- 설치형 Chrome 31/31 PASS.
- 설치형 Edge 31/31 PASS.
- 여섯 문서 HTML은 1280px 직접 열기, 이미지 로드, 가로 넘침, 페이지 오류, 외부 네트워크 리소스 0건을 통과했다.

## DBG-2026-08-24-005 — 구두 소개서의 새 화면이 메일 CID 목록에서 누락됨

### 증상과 원인

- v0.7.3 구두 기능 소개 원본에는 선택형 용존산소 화면이 추가됐지만, 메일 본문 생성기의 고정 이미지 목록은 이전 5장만 포함했다.
- 그대로 발송하면 새 화면이 상대경로 `screenshots/...`로 남아 메일 본문에서 깨질 수 있었다.

### 수정과 영구 차단책

- `prepare-oral-email.mjs`의 CID 목록에 v0.7.3 용존산소 화면을 추가해 본문 이미지 6장을 모두 `cid:`로 변환했다.
- 생성 검증에 상대경로 `src="screenshots/` 잔존 여부를 추가했다. 이후 구두 소개서에 화면을 추가하고 CID 목록 갱신을 빠뜨리면 생성 단계에서 즉시 실패한다.

### 재검증

- 메일 생성기 ESLint PASS.
- 생성 본문은 CID 참조 6개, manifest 이미지 6개, 외부 이미지 주소 0개, 스크립트 태그 0개다.
- GitHub 저장소와 v0.7.3 Release 링크, 선택형 용존산소 설명이 본문에 포함됐다.
- 발송 후 보낸편지함에서 두 메일 모두 실행본·상세설명서 2개와 CID 화면 6개의 파일명·바이트 수를 확인했다.
